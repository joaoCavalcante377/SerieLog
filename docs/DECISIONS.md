# Decisions

- Project lives in `serielog/` (working name; change `SITE_NAME` in `src/config/site.ts`).
- Next.js 16 scaffold: `cacheComponents`/`partialPrefetching` flags from the template were removed — they force Suspense around all dynamic access and are not needed for the MVP.
- Prisma 6 (not 7) pinned: stable `prisma-client-js` generator and `url` in the datasource.
- Password hashing: argon2 (`argon2` package).
- `User.username` is nullable so Google sign-ups can choose it later (AUTH-06); a CHECK enforces lowercase.
- Partial unique index (one WATCHING log per user+series), rating CHECKs (0.5 steps), Top-4 position CHECK and a DEFERRABLE `(listId, position)` constraint are hand-written in the init migration because Prisma cannot express them.
- `Series` → user-data relations use `onDelete: Restrict`: user actions never delete cached series rows; deleting a user cascades their own rows.
- Dates without time (`airDate`, `startedAt`, `finishedAt`) use `@db.Date` to avoid timezone drift.
- Rate limiting is DB-backed (`RateLimit` table, fixed window) — works across serverless instances; not atomic under heavy concurrency.
- CSP keeps `'unsafe-inline'` for scripts/styles (Next without nonces); nonce-based CSP is a Phase 8 follow-up.
- Header search bar is deferred to Phase 3 (needs TMDB); no non-functional controls shipped.
- shadcn/ui components are added on demand (from Phase 2) rather than bulk-installed.
- Auth simplified by request (Phase 2): email+password only, stateless JWT session (httpOnly cookie, 30 days) so users stay logged in. No Google OAuth (AUTH-06 deferred), no password recovery/email verification, no rate limiting yet (AUTH-07 → Phase 8). `Account`/`Session`/`VerificationToken` tables stay in the schema so OAuth can be added later without a migration rewrite.
- Route protection is done in server components via `requireUserId()` (redirects to `/entrar?callbackUrl=…`), not in `proxy.ts`, because argon2/Prisma do not run at the edge.
- Auth.js `authorize` re-uses `verifyCredentials`; mutation logic lives in `features/*/server/*` (user-id based, no session) so it is testable against Postgres; Server Actions only authenticate and delegate.
- Integration tests run against `serielog_test` (never the dev DB); `globalSetup` applies migrations, tests run serially.
- `/diario` is a protected placeholder until Phase 4.
- Phase 3: no `loading.tsx` on `/serie/[idslug]`. A loading boundary makes Next commit HTTP 200 before the page resolves, which turns unknown series into "200 + 404 page" and breaks the canonical 308 redirect. Real status codes win; only the first-ever visit of a series (TMDB sync) is slow. Home shelves still stream behind skeletons.
- "Popular reviews" has no popularity signal (likes are out of scope), so the series page shows the most recent reviews.
- Cast is fetched from TMDB per page view (Next fetch cache, 24h) and not stored; if TMDB is down the section is omitted.
- Episodes removed from TMDB are never deleted locally (user watch records reference them).
- Search results are not rate limited yet (Phase 8). Search/discover responses are cached by Next's fetch cache (5 min – 24 h).
- Genre filter on `/series` is a plain GET form (works without JS, URL is the state); pagination uses Previous/Next links.
- Series data and the TMDB logo (`public/tmdb-logo.svg`) are in the footer; the TMDB token only lives in `.env`.
- Phase 4: logged-out actions redirect to `/entrar?callbackUrl=<series>?acao=watchlist` (a page, not a modal, matching Phase 2's login page); the series page completes the queued watchlist add after login.
- Star clicks follow the spec literally: click N → N, click N again → N−0.5, again → N. Keyboard: arrows ±0.5, Home clears (or 0.5 when not clearable), End = 5. Component is `role="slider"`; stars themselves are mouse/touch only.
- Rating a series with no log creates a COMPLETED log dated today (rating implies watched). With an existing active/latest log, the rating is written to it instead.
- Any log creation removes the series from the watchlist; WATCHING logs never keep a finish date.
- Diary date = finishedAt, else startedAt, else the day it was logged (São Paulo). Ordering is `(diaryDate, createdAt, id)` via raw SQL so offset pages stay stable; "load more" is a Server Action and the client de-duplicates by id.
- `/[username]/diario` and `/[username]/watchlist` shipped in Phase 4 (the profile page itself is Phase 7). Only the owner sees edit/delete; every write still re-checks ownership.
- Dev deps added for component tests: `jsdom`, `@testing-library/*`. E2E uses Playwright against a production build and the `serielog_test` database (`pnpm build && pnpm test:e2e`).
- Phase 5: rule 1 ("first episode with no active log creates a WATCHING log") applies whenever there is no WATCHING log, so resuming a dropped or completed series creates a new log flagged `isRewatch`. `createMany … skipDuplicates` (ON CONFLICT DO NOTHING) makes concurrent marks safe with the partial unique index.
- Unmarking never touches logs, and the completion prompt only appears for an active WATCHING log (never auto-completes).
- Marking a season/series marks only aired episodes (specials included for "whole series", excluded from the percentage). Undated episodes count as not aired.
- "Novos episódios" = latest log COMPLETED while some aired, regular episodes are unwatched (and at least one is watched). The "Voltar a assistir" button moves that log back to WATCHING; it is never done silently.
- Season rating: one per user and season; "clear" deletes the row. The season header shows my rating read-only; editing happens in a dialog.
- Episode toggles use local optimistic state (not `useOptimistic`) so a successful save never flickers back while `router.refresh()` loads; failures roll back only that episode.
- "Mark all episodes" is an opt-in checkbox in the log form (shown for COMPLETED), not forced.
- Phase 6: dependency `@dnd-kit/core|sortable|utilities` for accessible drag-and-drop (built-in keyboard sensor and screen-reader announcements, localized to pt-BR); the handle is a real button.
- List editing locks the list row (`SELECT … FOR UPDATE`) so concurrent adds/removes/reorders never produce duplicate or gapped positions; reordering swaps positions inside one transaction thanks to the DEFERRABLE `(listId, position)` constraint, and is refused (CONFLICT) if the item set no longer matches (stale UI).
- The slug is generated once from the title and kept on edit so shared links keep working.
- Adding from the editor's search syncs the series from TMDB first (it may not be cached yet); the series-page menu uses the already cached series.
- "Popular lists" has no like signal: ordered by number of series, then newest. Private lists never appear in browse, user pages, metadata or the OG image, and respond 404 to anyone but the owner.
- Series cards in list covers use plain `<img>` (four tiny, lazy images per card) instead of `next/image`.
